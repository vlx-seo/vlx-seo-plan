Three animation decisions

Each block below puts what the homepage does today next to what I'm proposing. They're interactive — scroll them and watch, don't just read. There's a decision table at the end.

Decision 1 · affects 366 sites across 87 files

The scroll reveals

Every section fades in and slides up 24 px. Today framer-motion drives that, recalculating the style from JavaScript on every frame. The browser can do exactly the same thing for free if you ask it in CSS.

What it saves
The per-frame JavaScript work across 92 elements on the homepage. It also lets us pull framer-motion out of the sections near the fold, which is what drags it into the critical path in the first place.
Recommendation
Change it. This is the one of the three where nothing is lost: same effect, no cost. The "no animation" option is there only so you can see how much the effect actually contributes.

Decision 2 · homepage only

Dimming sections as they leave the screen

SectionFade drops each section to 0.4 opacity as it scrolls off the top. It's tied to the exact scroll position, so it recalculates continuously while the finger is moving. This one does look different, which is why the call is yours and not mine.

Decision 3 · the homepage H1

The headline that types itself

Visible change
A: none B and C: yes Option A is indistinguishable from what ships today.
What it saves
The loop never stops: as long as someone has the tab open, the H1 keeps rebuilding itself. That's constant main-thread work and battery drain on mobile.
SEO note
Whichever option wins, two things that are already handled correctly must survive: the server HTML always ships a complete word, and the effect stops under prefers-reduced-motion. Both are in the current code and neither should be touched.
Recommendation
Option A if you want to keep the effect exactly as it is, which is what I'd do. B and C are on the table in case you wanted to simplify the hero anyway.

About the counters. They count the style writes this page's own JavaScript makes, which is a stand-in for the work React does on the real site — useful for comparing the options against each other, not as a measurement of vlx.ai. The site figures (INP 244 ms, 92 animated elements on the homepage, 366 across the site) are measured, and live in docs/performance/PERF-AUDIT-PLAN-2026-08-18.md.

One detail about the demo. The reveals in decision 1 are triggered here with a scroll handler rather than IntersectionObserver, which is what the real implementation would use, so they behave the same in any context. What's being compared is who runs the animation — a JavaScript calculation per frame versus a single class change — not what triggers it, and the trigger is the same in both panes, so the comparison is fair.
